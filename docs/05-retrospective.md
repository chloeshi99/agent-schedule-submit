# 05 复盘（最难问题、学习收获、下一步）

## 1. 最难的问题

### 1.1 「动态决策」与「固定条件分支」的边界

题目有一条明确的判定口径：

> 允许采用预设流程作为执行骨架；仅有固定条件分支、自动重试或预设决策日志，
> **不视为完成 ReAct 决策要求**。

这是本项目最难的部分，难在**它不是功能问题，而是定义问题**。

**第一版的做法**：离线 Mock 里按 `last_tool` 分派到 `_after_read` / `_after_check_rules` /
`_after_query_slots` / `_after_save`，每个函数里再按观测内容分支。

功能上完全正确 —— 冲突会建议 19:00、缺失会补查、失败会重试。
但**形式上就是一个 if-else 状态机**。按题目的字面标准，这确实有被判为
「固定条件分支」的风险。

**最后的解法**不是把分支写得更巧妙，而是**让决策过程本身可被验证**：

1. **`Action` 增加 `decided_by` 字段** —— 显式记录「这一步的决策由哪个观测字段驱动」。
   每次决策都必须回答「我为什么做这个动作」，答案指向一个具体的观测字段，
   而不是「因为现在是第 3 步」。
2. **trace 增加 `decided_by` 列** —— 评审者打开 `examples/traces/*.jsonl` 就能逐行核对：
   第 2 步的决策依据是 `observation.missing_fields`，
   第 4 步的依据是 `observation.requested_conflicts`，一目了然。
3. **用测试证明「不同观测 → 不同动作」** —— 不靠叙述，靠断言：
   - `test_loop_is_model_driven_not_scripted`：后续步骤的 `decided_by` 必须互不相同
   - `test_observation_changes_next_action`：18:00 被占 vs 20:00 空闲 → 动作序列不同
   - `test_supplement_result_changes_rule_evaluation`：补查前后规则结论确实改变

**最有力的证据**是 `duplicate_submit_twice` 的 trace：同一套请求连续跑两次，
前 4 步动作序列**完全相同**，仅因第 4 步 `save_draft` 返回
`saved` vs `duplicate`，第 5 步的决策就随之不同。
这不是「按步号推进的脚本」能产生的行为。

**我承认的边界**：离线 Mock 终究是确定性策略引擎，决策空间被预先枚举。
它证明了**流程与契约的正确性**，没有证明**真实模型的决策质量**。
这一点在 `03-evaluation.md` 第 7 节写得很直白，不用 Mock 结果冒充模型效果。

### 1.2 补查回写：一个「看起来能跑但实际空转」的缺陷

第一版 `read_material(fields=[...])` 返回补查结果，但**没有回写到素材**。
于是 `check_rules` 拿到的还是原始素材，缺失字段依然缺失，风险等级不变。

表现是：补查这一步**纯粹浪费了一次工具调用**，模型补查完还是只能阻断。

这个问题 AI 最初没有发现，是我读补查链路时发现的。修复方式是引入
`ToolContext.overlay`（内存 overlay，不修改原始数据），补查字段写入 overlay，
`check_rules` 通过 `effective_material()` 取叠加后的副本。

**教训**：工具链里「读取 → 补查 → 重新评估」这种闭环，
必须确认**数据真的回到了下一环**。光看返回值像是正常的。

### 1.3 幂等的「两个维度」

第一版的幂等设计：应用层用 `request_key = material_id|date|start|channel|content_hash`，
数据库层加 `UNIQUE(material_id, date, start_time)`。

看起来是「应用层 + 数据库层」双保险，但有个洞：
**内容改了**（`content_hash` 变 → `request_key` 变）**但排期没改**时，
应用层认为是新请求，数据库层却认为违反唯一约束 → 冲突 → 被误判成「保存失败」。

修复：`IntegrityError` 时**同时**按两个维度回查 ——
`request_key` 匹配 → duplicate；`(material_id, date, start_time)` 匹配 → duplicate；
两者都查不到 → 才是真实失败。

**教训**：双保险的「保险」之间也要对齐语义，否则两层会打架。

### 1.4 「不要擅自更改硬性要求」与「要给出可用建议」的张力

题目的两个要求看起来矛盾：
- 未经用户同意不得擅自改变硬性发布要求
- 但冲突时要给出替代时段（参考实例：18:00 被占 → 建议 19:00）

我的解法是把「建议」和「执行」分开：

```
给出建议  19:00 + pending_confirmations(change_publish_time)   ← 模型做
执行落库  save_draft                                             ← 需要用户确认才做
```

关键在于**冲突路径根本不产出 `save_draft` 调用**，
所以「不擅自更改」不是靠提示词约束，而是靠**工具调用序列**保证的。
`tests/test_cases.py::test_conflict_case_does_not_write_draft` 断言草稿数为 0。

### 1.5 幂等之外的两个隐蔽失败

**（a）`save_draft` 返回 `status="saved"` 但没有 `draft_id`**

这在正常路径不会发生，但如果模型或工具层出了问题，
`draft_status="saved"` 就会进入最终结果，变成**虚报保存成功**。

修复：`_finalize` 中检查 `draft_status == "saved"` 且无 `draft_id` → **改判为 `failed`**。

**（b）SQLite 连接泄漏**

`with sqlite3.connect(...) as conn` 这个写法有个陷阱：
**它只管理事务（commit/rollback），不关闭连接**。
每次工具调用开一次连接、用完就丢，句柄一直累积。
平时测试看不出来（进程退出时操作系统会回收），但我在 Windows 上删除临时库文件时
遇到了 `PermissionError: 另一个程序正在使用此文件` —— 这才暴露了问题。

修复：引入 `@contextmanager _cursor()`，在 `finally` 里显式 `conn.close()`，
并补了回归测试 `test_connections_are_closed_not_leaked`（操作 20 轮后文件仍可删除）。

**教训**：题目标明的「关键缺陷」要逐条构造攻击路径，而不是确认正常路径没坏。
资源泄漏这类问题在短测试里不显形，需要**主动构造验证方式**（比如专门删文件）。

## 2. 学习收获

### 2.1 工程层面

| 收获 | 具体体会 |
|---|---|
| **分层比框架重要** | 把「可验证的计算」放确定性代码，把「需要判断」放模型，业务规则才能回归测试。规则引擎 18 个单测全靠这个分层 |
| **提示词是引导，代码是保证** | 每条提示词约束都配一道代码层强制（`published=False`、冲突不落库、缺 `draft_id` 改判 failed）。模型不完全听话时系统依然安全 |
| **幂等要应用层 + 数据库层，且语义对齐** | 见 1.3 |
| **测试要构造攻击路径** | 「模型试图声称已发布」「保存返回成功但无 draft_id」「内容变更但排期相同」——这三个正常路径测不出来 |
| **交付材料要自动生成** | `scripts/gen_outputs.py` 让文档里的每个数字都来自实际输出，避免文档与代码漂移 |

### 2.2 关于 AI 协作

| 收获 | 具体体会 |
|---|---|
| **AI 擅长铺量，不擅长发现语义漏洞** | 补查不回写、幂等只看一个维度、`.gitignore` 忽略交付物 —— 这三个都是 AI 生成的代码里的真实缺陷，靠人工读代码发现 |
| **把 AI 当执行者，不当判断者** | 让 AI 实现规则引擎很快，但「哪些规则该阻断、哪些该提示」是我定的 |
| **用可执行的断言替代描述性文档** | 「决策是观测驱动的」这句话没有说服力；`assert decided_by 各步不同` 才有 |
| **文档里必须写清边界** | 明确写「Mock 不证明真实模型决策效果」比夸大完成度更安全，也符合题目要求 |

## 3. 下一步

按优先级排列（若继续投入）：

### 3.1 优先：真实模型通道的效果评测（当前最大缺口）

现状：真实模型通道代码已实现，但**未经评测**。

计划：
1. 配置密钥，在 7 个用例上跑真实模型，与离线 Mock 结果**逐字段对比**
2. 统计决策一致率、越权尝试次数（模型是否试图 `published=true`）、重试次数
3. 重点看失败模式：是否擅自改时间、是否提前结束、是否臆测缺失值
4. 把对比结果补进 `03-evaluation.md`，形成「Mock vs 真实模型」的对照表

**这一步能把「流程正确」升级为「决策质量达标」，是最高价值的增量。**

### 3.2 其次：把「已确认」变成真实的多轮交互

当前 `--confirm` 是命令行开关，不是真正的对话确认。

计划：
- 支持 `--confirm-prompt` 模式：模型给出待确认项后，CLI 交互式询问，
  用户回答「改用 19:00」后再保存
- 记录确认动作进 trace，让「确认边界」有更完整的证据链

### 3.3 技术债与工程完善

| 项 | 说明 |
|---|---|
| **请求解析** | 规则式正则 → 改为模型抽取（复用同一 LLMClient，输出结构化 JSON） |
| **补查数据源** | 模拟数据 → 接入真实素材库/审核系统的只读查询接口 |
| **冲突粒度** | 小时粒度 → 支持分钟粒度与渠道级匹配 |
| **存储** | SQLite → PostgreSQL，增加并发写与事务隔离测试 |
| **可观测性** | JSONL trace → 结构化日志 + 指标（决策分布、平均步数、失败率） |
| **CI** | 加 GitHub Actions：`pytest` + `check_secrets` + `gen_outputs` 一致性校验 |
| **HTTP API** | 题目允许 CLI/HTTP/Notebook 三选一，若需要可加一个 FastAPI 薄封装 |

### 3.4 架构演进

若需求升级为**多素材批量排期**（一次请求排多个素材，或处理「先到先得」的竞争场景），
现在的单素材串行循环就不够了，需要：

- 引入**全局时段占用视图**（跨素材冲突）
- 用 LangGraph 的条件边表达「成功/冲突/阻断」的分叉，或自建调度层
- 引入**回溯机制**：某素材被阻断后释放已占用的时段

这是我认为迁移到 LangGraph 的第一个真实触发点 ——
当前单素材规模下，框架带来的抽象成本高于收益。

## 4. 总结

这个项目最有价值的产出不是「排期 Agent 能跑」，而是**两条把 AI 行为关进笼子的机制**：

1. **决策可追溯** —— 每一步决策都标注了它依据的观测字段，可逐行核对
2. **越权不可达** —— 发布、擅改时间、谎报成功，三条路都在代码层被封死，
   模型说什么都无效

题目说「高分依据是冲突调整、确认边界与防重复」，也把「越权发布或虚报保存成功」
列为关键缺陷。这套设计正是围绕这几点展开的 —— 而且**不依赖模型自觉**。

至于「模型是不是真的会思考」，离线 Mock 给不出答案，这一点我没有回避，
而是把它写进了文档的局限章节。
